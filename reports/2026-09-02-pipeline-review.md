## 0. 요청 해석과 경고 (먼저)

**해석.** "그간 동향 + 설계도 → 문제점 → 실매수 가능한 자기보완 루프로의 재설계안"으로 읽었다. 세 층을 분리해 쓴다: ①무엇이 일어났나(사실) ②왜 그런가(진단) ③무엇을 바꿔야 하나(What/Why/판정 기준). 구현 방법(How)은 단계별 최소 수준까지만 적고, 파라미터 수치는 확정하지 않는다.

**경고 1 — 목적 이탈 위험.** 이 레포는 105일 동안 정책을 **1.0 → 2.36까지 37회** 올렸고, 그 사이 왕복 매매는 19건이다. "실매수 형태"를 만드는 작업이 또 하나의 룰·기능 추가로 흐르면 지금까지의 실패를 반복한다. 이 리포트의 결론은 **"더하지 말고 빼라"** 이고, 그 다음이 **"체결 결정권을 LLM에서 코드로 옮겨라"** 다.

**경고 2 — 현 상태는 실매수와 거리가 멀다.** 브로커 연결 0건, 체결 주체가 LLM 세션, 승인 채널이 단방향(카톡 나에게 보내기), 손익 지표 전부 미달(PF 0.46). 지금 실계좌를 붙이면 검증되지 않은 룰 스택이 실제 돈으로 휩쏘를 반복한다. 따라서 이 리포트는 "언제 붙일 수 있나"의 **사전 등록된 통과 기준**을 정하는 데 무게를 둔다.

## 3. 설계도 읽기 — 실제로 어떻게 도는가

```
[데이터 레이어 · GitHub Actions · 결정론]
  fetch_prices(개장 전후 30분 간격) → market_snapshot · mark_to_market · score_candidates · compute_allocation
  fetch_history(주간) → backtest_strategy · momentum_signal (듀얼모멘텀 바스켓)
  fetch_news / flows / catalysts / fundamentals / valuation / consensus(고장)
  intraday_monitor(30분) → 트리거 평가 → 카톡 신호만
        │
[의사결정 레이어 · Claude 루틴 · 비결정론 · 하루 6회]
  프롬프트(00/06/09/12/15/18) → 핫패스 적재(watchlist·policy·weekly_plan·portfolio·lessons ≈ 1MB)
  → 웹검색 → 게이트 사다리(신선도·heat·R/R·chase·catalyst·estimate·sector avoid·회복단계·레짐)
  → **가상 체결을 LLM 이 trade_log/portfolio 에 직접 기록** → 리포트·lessons 갱신 → commit/push
        │
[감사·보완 레이어]
  pipeline_audit(매일) · self_audit(일 17시, 기계) → findings
  sunday_policy_review(일 20시, LLM) → disposition · policy 패치 → 다음 주 루틴이 읽음
```

설계 의도는 명확하고 문서화도 훌륭하다. 문제는 **결정권의 위치**다. 백테스트로 검증된 것은 데이터 레이어의 `momentum_signal` 뿐인데, 그 신호는 "1순위 후보"로 격하되어 LLM 루틴의 게이트 사다리를 통과해야 하고, 그 사다리는 백테스트에서 가치를 파괴한다고 판정된 오버레이(하드스톱·트레일링)와 백테스트 자체가 없는 룰(orange/red 단계, give-back, R/R 하한, thesis 무효화, estimate gate, 회복단계)로 이루어져 있다.

## 4. 문제점 진단 — 근본 원인 6가지

### P1. 검증된 전략과 실제 운용이 다르다 (전략-집행 괴리) — 확정
- 백테스트 권장안: Top10·42거래일 리밸·MA200·항시투자·**오버레이 없음**. 라이브 설정: Top6·21일·점수 하한 30·tracked_only + 전체 게이트 사다리.
- 오늘(9/2) 신호: 자격 10종 중 매수 가능 2종(SK하이닉스 — 1주 164만원이라 사이징 배제, 삼성SDI — 점수 24.8로 하한 미달·R/R 미달로 09시 기각). 실제 보유 5종은 **전부 `skipped_below_floor`**. 즉 검증된 엔진은 한 종목도 들고 있지 않다.
- 청산 오버레이 백테스트(`backtest_exit_overlay.json`): 4개 설정·구간 중 3개에서 오버레이가 **-39.9 ~ -253.5%p** 가치 파괴, 휩쏘 59/87건. 파이프라인은 이 결과를 7/8 에 얻고도 오버레이를 라이브로 유지했다(래칫 shadow 만 관측).
- 결과: "듀얼모멘텀으로 검증했다"는 문장과 "은행 3종을 R/R 룰로 관리한다"는 현실이 공존한다. **어떤 성과가 나와도 무엇을 검증한 것인지 알 수 없다.**

### P2. 룰 스택이 수익원(추세)을 잘라낸다 — 확정
- 휩쏘 77.8%. 손실 스톱 9건 중 7건이 5일 내 회복.
- R/R 하한(1.1) 룰의 순환: 목표에 다가가면 분자가 얇아져 R/R 이 떨어지고 → 처방은 손절 상향 → 스톱이 가격에 붙어 노이즈 체결 → lessons 9/1 항목이 스스로 "처방이 아니라 산식이 문제"라고 적었다. **룰이 룰을 부르는 구조.**
- 청산 룰 13종 × 표본 19건. 어느 룰도 통계적으로 살아남을 표본이 없다.
- 이것은 개별 파라미터 조정으로 풀리지 않는다. 오버레이를 **통째로 shadow 로 내리고** 백테스트가 지지하는 최소 청산(리밸런스 회전 + 추세 이탈 + 하드스톱 1개)만 남기는 결정이 필요하다.

### P3. 자기보완 루프가 '설명'을 학습하고 '손익'을 학습하지 않는다 — 확정
- 학습 단위가 "목표가 vs 종가 ±5% 괴리의 사유 분류"다. 보유 종목마다 매일 발생하므로 하루 3~6건이 자동 생성되고, 대부분 같은 매크로 서사의 반복이다(섹터 오차 37건).
- 학습 → 정책 반영 경로가 "산문 → 일요일 LLM 리뷰 → policy 패치"라서 **표본 없는 패치**가 구조적으로 쉽다. 패치 동결 원칙(v2.22)이 있지만 "데이터 버그 수정" "shadow 임계 조정" 이름으로 계속 우회됐다.
- 손익 기반 채점(rule_attribution·forgone·inference_scorecard)은 존재하지만 **정책 결정의 입력이 아니라 감사 리포트의 부록**이다. 9주 open 인 두 finding 이 그 증거다.
- 기회비용오차 0건(2-3 참조) — 루프가 최대 실패를 못 본다.

### P4. 콘텍스트 포화 — 루프의 피드백 채널이 막혔다 — 확정
- 핫패스 의무 적재 ≈ 1MB(lessons 537KB + watchlist 161KB + policy 127KB + weekly_plan 69KB + 프롬프트 67KB). 한국어 기준 수십만 토큰이라 **"모든 루틴은 lessons.md 를 먼저 읽는다"는 전제가 물리적으로 성립하지 않는다.**
- 감사가 20일 연속 FAIL 로 표시하지만 처분은 defer. compact_state.py 가 있어도 ✅codify 마커를 남기는 루틴이 없어 이관량 0.
- 결과: 루틴은 규칙 누락·판단 열화가 일어나도 그것을 인지하지 못한다. lessons 의 "루틴 오차" 항목들(묵은 뉴스를 시세로 오인 6/8, 크래시를 데이터 지연으로 오판 7/16, 전일 종가 재활용 7/17)은 그 증상이다.

### P5. 계좌 크기와 유니버스가 맞지 않는다 — 확정
- 500만원 계좌에 SK하이닉스 1주 164만원(33%), 삼성SDI 56만원, 한화에어로 116만원. 상위 모멘텀 종목은 **1주가 종목당 상한(30~35%)을 넘거나 딱 1주**다.
- 따라서 "Top6 동일가중"은 이 계좌에서 집행 불가능하고, 실제로는 저가 은행주가 채워진다(P1 의 직접 원인 중 하나). 부분익절 50% 도 "2주 중 1주"라 사실상 전량 청산이다.
- 백테스트는 정수주 제약 없이 계산됐으므로 **백테스트 성과는 이 계좌 크기에서 재현될 수 없다.**

### P6. 실체결 관점의 결격 — 확정
1. **체결 주체가 LLM.** 가격을 읽고 수량을 정하고 원장에 쓰는 행위가 1MB 콘텍스트를 든 비결정론 세션 안에서 일어난다. 원장 정합성 검사(reconcile·provenance gate)가 뒤에서 잡아주지만, 실계좌에서는 "잘못 낸 주문"을 사후 검사로 되돌릴 수 없다.
2. **브로커 연결 0.** 실주문·체결·잔고 대사 코드가 없다. 슬리피지 0.2% 는 가정값이며 실측된 적 없다.
3. **승인 채널이 단방향.** 설계는 "Tier 2 실매수는 카톡 승인 후"인데 카톡 '나에게 보내기'는 회신을 받을 수 없다.
4. **kill switch 가 부분 배선.** `proactive_inference.kill_switch` 는 장중 모니터(`check_intraday_alerts.py`)만 확인한다. 루틴의 체결 경로에는 코드 수준 정지 장치가 없다.
5. **슬롯 결측 = 손절 미집행.** 18시 결측 2회. 실계좌였다면 그날 종가 손절이 사라졌다.
6. 컨센서스 수집 한 달째 실패, 뉴스 3겹 실패(8/22) 등 데이터 결손이 조용히 진행된다.

## 6. '실매수 가능한 형태'로 가는 재설계 (What / Why / 판정 기준)

### 6-0. 원칙 (확정 제안)
1. **빼기 우선.** 새 룰·새 레이어·새 슬롯을 만들지 않는다. 기존 룰은 "백테스트 지지" 또는 "shadow" 둘 중 하나로 분류한다.
2. **체결 결정권은 코드에.** 매수/매도/수량은 결정론적 스크립트가 파일(주문 의도)로 산출한다. LLM 은 ①후보 발굴(근거 URL 필수) ②거부권(사유 기록, 기본은 통과) ③서사·리포트만 맡는다. LLM 이 원장에 직접 쓰지 않는다.
3. **사전 등록된 통과 기준.** 단계 이동은 사람의 감(느낌)이 아니라 미리 적어 둔 숫자로만 한다. 기준을 못 넘으면 이전 단계로 돌아간다.
4. **한 번에 한 실험.** 파라미터 변경은 shadow 로 N 왕복 관측 후에만 라이브. 동시에 두 개를 바꾸지 않는다.

### 6-1. 단계

**Stage 0 — 동결·측정 (즉시, 2~4주)** · 유력안
- 정책 파라미터 **전면 동결**(버그 수정만). 스크립트 감사는 계속.
- **"명세 그대로의 전략" 그림자 계좌**를 스크립트로 매일 자동 산출: momentum_signal 바스켓을 리밸런스 주기대로 오버레이 없이 정수주 제약 포함으로 페이퍼 체결. 라이브 계좌와 **같은 날짜 기준으로 나란히** 기록.
  - 왜: P1 을 숫자로 닫는다. "LLM+게이트 레이어가 검증 전략에 더하는가, 빼는가"가 유일하게 중요한 질문이고, 지금은 답할 데이터가 없다.
- 핫패스 다이어트: lessons.md 는 "확정 룰 표 ≤ 60KB" 만 남기고 전문은 archive. 루틴이 읽는 것은 룰 표 + 2페이지 체크리스트뿐.
- 성공 지표 **하나** 사전 등록: 비용 차감 후 60거래일 롤링 수익률 vs (a) KOSPI (b) 그림자 계좌. 보조: PF·휩쏘율·주식비중 밴드 이탈 일수.
- 기회비용오차 채점 수정: bull/neutral tier 에서 deploy 권고가 켜져 있는데 미배치한 날의 forgone 을 산입.

**Stage 1 — 실행의 코드화·룰 감량 (4~8주)** · 유력안
- 주문 의도 파일(예: `state/order_intents.json`)을 결정론 스크립트가 생성: 진입=바스켓 변경분, 청산=리밸런스 회전 + 추세 이탈 + 하드스톱 1개. 나머지 청산 룰(orange/red·give-back·R/R 하한 손절 상향·트레일링 2단·shock deferral)은 **shadow 로 강등**해 관측만.
- LLM 루틴의 역할 축소: 주문 의도에 대한 **거부권**(사유+근거 URL, 기본 통과) + 후보 승격 제안 + 리포트. 거부 이력도 채점(거부가 옳았는지 t+5/t+20).
- 계좌-유니버스 정합(P5) 결정: (a) 페이퍼 자본을 실제 투입 예정 자본으로 맞추고 top_n 을 그에 맞게 줄인다 (b) 또는 유니버스에 정수주 제약을 넣어 백테스트를 재실행한다. **둘 중 하나는 반드시** — 지금처럼 "백테스트는 무제약, 라이브는 1주 단위"는 안 된다. → 확인 필요(실투입 자본 규모).
- 슬롯 신뢰도 SLO: 18시(청산 판정) 슬롯의 결정론 부분(EOD 마크·스톱 판정)을 Actions 워크플로로 이중화. LLM 루틴이 미발화해도 원장은 닫힌다.

**Stage 2 — 모의투자 계좌 연결 (8~12주)** · 유력안
- 증권사 Open API 모의투자 계좌(예: 한국투자증권 KIS)에 **주문 의도 → 실제 주문** 스크립트를 붙인다. 이 단계의 목적은 수익이 아니라 **슬리피지·체결률·대사 오류율의 실측**이다.
- 안전 못(코드 수준, 전부 하드): kill switch 파일 존재 시 주문 0건 / 일일 최대 주문 수·최대 금액 / 시세 신선도 > X분이면 주문 금지 / 09:00~15:20 외 주문 금지 / 매일 브로커 잔고 ↔ portfolio.json 대사, 불일치 시 **자동 정지**.
- 승인 채널을 양방향으로: 카톡 단방향 대신 GitHub Issue 라벨·Telegram 봇·간단한 승인 페이지 중 하나. Tier 2 매수는 승인 없으면 만료.

**Stage 3 — 소액 실매수** · 보류(기준 충족 전까지)
- 1슬롯·소액부터. 지표가 유지되는 동안만 단계적으로 확대. 주간 리뷰는 룰 표와 대사 결과만 본다.

### 6-2. 단계 이동 Go / No-Go (사전 등록 제안 — 수치는 유력안, 확정은 사용자 몫)

| 기준 | Stage 0→1 | Stage 1→2 | Stage 2→3 |
|---|---|---|---|
| 그림자 vs 라이브 격차 측정 | 20거래일 이상 나란히 기록 | 라이브(코드 체결) ≥ 그림자 -1%p | 동일 |
| 왕복 표본 | — | ≥ 20건 (오버레이 감량 후) | ≥ 40건 누적 |
| PF / 휩쏘율 | 측정만 | PF > 1.0 · 휩쏘 < 50% | PF > 1.2 · 휩쏘 < 40% |
| vs KOSPI (비용 차감, 60거래일) | 측정만 | ≥ -2%p | ≥ 0%p |
| 주식비중 밴드 이탈 | 측정만 | 이탈 일수 < 20% | < 10% |
| 슬롯·원장 신뢰도 | — | 18시 EOD 100% (20거래일) | 대사 불일치 0건 (40거래일) |
| 정책 패치 | 0회 | shadow 경유만 | shadow 경유만 |
| 실측 슬리피지 | — | — | 가정치(0.2%) 대비 ≤ 2배 |

기준 미달 시 이전 단계로 복귀하고, 복귀 사유는 Decision Log 에 남긴다.
